# 80 — USER INTERFACE & COMPONENT GOVERNANCE

## 1. UI Architecture & Design System
1. **Centralized UI Library**: NexaBiz standardizes presentation components using a centralized design system built upon `shadcn_flutter`.
2. **Central Design Tokens**: Colors, typography, spacing, shadows, border radii, and animation durations MUST consume centralized theme tokens. Ad-hoc styling, arbitrary color hex codes, and inline custom text styles are FORBIDDEN.

---

## 2. Component Hierarchy & Reusability
1. **Shared Component Primitives**: Presentation pages MUST compose layouts using standard shared component primitives:
   * Layouts & Containers: Page scaffolds, cards, responsive grids.
   * Navigation: Sidebars, tabs, breadcrumbs, app bars.
   * Input & Forms: Form fields, text inputs, search selectors, date pickers, dropdowns.
   * Feedback & Status: Buttons, dialogs, alert banners, status chips, loading skeletons, empty state views, error state views.
   * Data Presentation: Tables, data grids, tree views, summary cards.
2. **No Page-Level Reinvention**: Creating page-specific widget reimplementations of standard components (e.g., custom button widgets or custom status badges) when a shared component exists is STRICTLY FORBIDDEN.

---

## 3. Responsibilities & UI Limits
Presentation widgets MUST remain purely presentational. Widgets MUST NOT own or execute:
* Accounting logic or journal entry calculations.
* Stock movement posting or inventory cost layer resolution.
* Tenant isolation enforcement or raw SQL queries.
* Security role determination or direct API communication.
* Multi-currency exchange rate calculations.

Widgets MUST interact with application logic solely by submitting user inputs to Riverpod UI controllers/use-cases and rendering state updates.

---

## 4. View States & UX Standards
1. **Mandatory View States**: Every data-driven UI screen MUST explicitly support four canonical view states:
   * `Loading`: Displays standard shimmer/skeleton loading indicators.
   * `Content`: Displays populated data views.
   * `Empty`: Displays standardized empty state graphics and descriptive guidance.
   * `Error`: Displays localized error messaging with retry actions.
2. **Form Validation UX**: Input forms MUST provide inline validation messaging using domain-validated rules without locking or freezing the UI thread.

---

## 5. Accessibility & Responsiveness
1. **Responsive Breakpoints**: UI layouts MUST adapt gracefully across mobile, tablet, and desktop viewports using centralized breakpoint rules.
2. **Accessibility**: Form elements, icons, and interactive buttons MUST include descriptive accessibility semantics (`Semantics` widget) and support keyboard navigation.
