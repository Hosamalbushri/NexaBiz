# PACKAGE_RECEIPTS_PAYMENTS_RP01_FORENSIC_DISCOVERY.md

## Executive Summary
This document delivers the forensic discovery audit of the Receipts & Payments module (`RP-01`) prior to architectural hardening.

The audit analyzed domain entities, database persistence, transaction lifecycles, accounting journal generation, cash register integration, multi-currency conversion, multi-tenant isolation, offline synchronization, and component dependencies.

---

## 1. Domain Architecture & Complete Flow Trace

### Complete Transaction Flow
$$\text{Receipt / Payment Draft} \longrightarrow \text{Voucher Allocation} \longrightarrow \text{Cash/Bank Account} \longrightarrow \text{Party Allocations} \longrightarrow \text{Journal Posting} \longrightarrow \text{Sync Queue}$$

1. **Document Identity:** Every transaction is identified by a unique UUID (`uuid`), a sequence document number (`transactionNumber`), a `companyId` tenant scope, and an operation type (`receipt`, `payment`, `transfer`, `currencyExchange`).
2. **Transaction Types:**
   - **Receipt (قبض):** Inflow of money into Cash/Bank account credited against a Customer Receivable account, Revenue account, or Party account.
   - **Payment (صرف):** Outflow of money from Cash/Bank account debited against a Supplier Payable account, Expense account, or Party account.
   - **Transfer (نقل):** Outflow from source Cash Box to destination Cash Box.
   - **Currency Exchange (مصارفة):** Conversion between currencies with FX gain/loss journal reconciliation.
3. **Lifecycle States:**
   - `unposted` $\rightarrow$ `posted` / `cancelled` (with `deletedAt` for soft-deletes).
   - Posted documents are immutable; updates or cancellations trigger period validation and journal voiding (`voidBySource`).

## 3. Accounting Integration Analysis
Accounting entries are generated by `AccountingRpLedgerAdapter`:
- **Receipt Posting:**
  - DEBIT: Cash Box Account (`cashAccountId`) in cash currency.
  - CREDIT: Counter Account(s) (`accountId` in allocation lines) in allocation currency.
- **Payment Posting:**
  - DEBIT: Counter Account(s) (`accountId` in allocation lines) in allocation currency.
  - CREDIT: Cash Box Account (`cashAccountId`) in cash currency.
- **Multi-Currency Reconciliation:**
  - Base currency equivalents (`baseDebit`, `baseCredit`) are computed using `exchangeRate` snapshots.
  - Currency Exchange calculates `baseDiff`; discrepancies exceeding threshold generate DEBIT `FX Loss` or CREDIT `FX Gain` lines.

## 4. Architectural Vulnerabilities & Duplications Identified

1. **Header vs Line State Duplication:**
   - `FinancialTransaction` maintains header counter fields (`counterAccountId`, `counterAmount`, `counterCurrencyCode`, `counterExchangeRate`) alongside multi-line `linesJson`.
   - `resolvedLines` synthesizes header fallback when `lines` is empty. A unified allocation structure will streamline domain integrity.
2. **Dashboard Cash Classification:**
   - `dashboardSummary()` uses custom SQL with hardcoded `LIKE '1211%'` (cash) and `LIKE '1212%'` (bank) code prefixes. It should query explicit account system keys (`systemKey`) or Cash Register links.
3. **Multi-Company Scoping:**
   - Repository queries enforce tenant scope via `_tenantScoped(t)` (`companyId = currentCompanyId`).

## 5. Offline & Synchronization Behavior
- Local operations set `syncStatus = 'pending'` and enqueue operations into `SyncQueue`.
- `applyRemotePayload()` performs version checks (`remoteVersion > existing.version`) to prevent overwriting modified local data and flag sync conflicts (`SyncStatus.conflict`).
